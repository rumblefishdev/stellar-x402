# Design decisions of task 0009

All emerged during implementation and the PR #41 reviews ([R-pr41-reviews.md](R-pr41-reviews.md));
none came from the plan.

1. **A repeat is answered from the record before the checks run.** ADR 0006's replay rule needs it (see Issues). The fingerprint still has to match exactly, so nothing new gets through. The checks run for every first call.
2. **A failure before anything was signed ends the record as `rejected`.** The same payload then gets the same failure, so the client retries by signing a new payment (new nonce). Examples: no channel in time, the simulation, the fee ceiling, a hook refusal. Reopening a record would need a store operation the port doesn't have.
3. **A thrown send that may have reached the network keeps the record open.** That's an attempt `sent: "unknown"`. The answer is `settlement_pending` with its hash, and 0019 resolves it.
4. **The balance-change check is ours** (`expectTransfer`), because upstream's event check is private and runs only on the client's simulation, not the pool's. It reads the events the same way.
5. **The settle module takes the pool as a `Submitter` interface,** so the settler's unit tests use a fake submitter. Amended by decision 27: `main()`'s wiring is now also tested on the real pool through `FakeRpc`.
6. **New fixed codes, named like upstream's:** `settle_exact_stellar_*` for settle-stage failures, plus `invalid_exact_stellar_payload_payer_auth_entries` and `…_nonce_already_used`. Amended by decision 19: `…_payer_auth_entries` is a `/verify` reason too, and `/settle` sends it from its re-check.
7. **`SETTLE_BUDGET_MS`** is a config value, so the ADR 0011 budget can follow the load balancer's settings. Its default is now 30 s (decision 17).
8. **`/settle` rechecks the auth expiry at the pool's floor of 2 ledgers** (Adam, 0018's PR #33 review; spine AD-22). `settleCheck(checks)` in `main.ts` is `createChecker` with `SETTLE_MIN_VALIDITY_LEDGERS` = 2 in place of `MIN_VALIDITY_LEDGERS`. `/verify`'s larger minimum leaves room for the time between the two calls; rechecking with it refused, at `/settle`, payments the pool would still sign, after the resource was served.
9. **`/settle`'s `payer` is a string or absent,** with no settle-side code: every `payer` in a settle answer comes from `createChecker`, which drops a non-string one (0018 decision 20), or from the record, which stores the checked payer. A test runs a settle through the real `createChecker` with an upstream `payer` of 5.
10. **A fee or ledger refusal after `/verify` accepted keeps its answer and is flagged** (Adam, 0018's PR #33 review, asked to define it; to confirm in the 0009 PR). The answer stays `success: false` with `settle_exact_stellar_fee_exceeds_maximum` or `…_signature_expiration_too_soon`, the record ends `rejected`, nothing was sent, and the client needs a new payment (decision 2). It also means `/verify` and the pool disagreed: a new fee-stats reading or escalation raised the fee, or the call waited too long for a channel. So it logs `settlement_refused_after_verify` (warn) and counts `settlement_refused_after_verify_total` by reason and stage (decision 38), for 0027's alerts.
11. **A timeout answer ends what it says was never signed** (PR #41 review). The pool checks `deadline` only while it waits for a channel, so a call that already had one could still sign and send after `/settle` answered `settle_exact_stellar_timeout`; the client would pay again with a new nonce. When the budget runs out, `outOfBudget` moves a `claimed` record (no hash) to `rejected` with `…_timeout`, by compare-and-set, and runs `onFinal`, since `beforeSubmit` had allowed it. `addHash` then refuses the record, so `onSigned` throws and the pool sends nothing. A record that already has a hash stays open, and the answer is `settlement_pending`. A same-payload retry now gets the timeout again rather than a late success; the client signs a new payment, as in decision 2.
12. **Nothing is submitted once the checks and `beforeSubmit` used up the budget** (PR #41 review). The record ends as in decision 11.
13. **A repeat waits for a record with no hash until the first call's budget ends, counted from the first call's start** (`createdAt`, taken before its checks) (PR #41 reviews). It first waited `SETTLE_TIMEOUT_MS` and then its own budget; anchored on its own start, a repeat whose checks were slow could answer `…_timeout` before the first call signed (Adam, second review). Now it waits until `createdAt + SETTLE_BUDGET_MS` and then ends the record itself, by the same compare-and-set as decision 11, before it answers `…_timeout`. A record with a hash still waits `SETTLE_TIMEOUT_MS`.
14. **A refusal stands when the store can't record it** (PR #41 review). The failed write is logged (`settlement_record_failed`) and the hook's refusal is the answer, not a 500. The record stays `claimed` with no hash. A repeat once the budget is over ends it (decision 13) and gets `…_timeout` at once, not after a full wait: the hook's own reason is lost with the failed write, and either way the client signs a new payment. A thrown error before the claim, such as upstream verify failing, stays a 500, as the spine says (0018 decision 16).
15. **When the store fails after the pool answered, the answer is the pool's result** (PR #41 review). It used to be `unexpected_settle_error` with no hash, even for a payment that landed. Now a success is `success: true` with the pool's hash, and anything else is its fixed reason with the hash. A success carries the `EXTENSION-RESPONSES` header from the record as it would have been stored (0031 DD2, second review); there is no `markSuccessAnswered` and no `onSuccess` without a stored record. 0019 finishes the record. Likewise, a send that may have reached the network, followed by a store failure, is `settlement_pending` with that send's hash, not `unexpected_settle_error`.
16. **A success is answered once per record** (okarcz, 2026-10-15, Adam's proposal from the second review; AD-6 and ADR 0006 amended). Every same-fingerprint repeat used to get `success: true` and the header, so a seller delivered every request carrying one payment header (Adam: 4 × 200 for one charge on testnet). Now `markSuccessAnswered` (a new store compare-and-set on `successAnsweredAt`) lets one caller answer `success`; every later one gets `settle_exact_stellar_already_settled` with the hash and no header. `settlement_pending` doesn't count, so upstream's one retry after it still gets the success, and a call whose client left (the route's `AbortSignal`) marks nothing. The cost: a seller that lost our `success` answer can't get it again. If the mark can't be written, the answer is the success: the payment landed.
17. **`SETTLE_BUDGET_MS` 30 s and `SETTLE_TIMEOUT_MS` 20 s** (okarcz, 2026-10-15, Adam's numbers; ADR 0011 amended). The 90 s budget equalled `HTTPFacilitatorClient`'s 90 s timeout, whose timer starts before the request, so the seller always gave up first and our pending answer went to a closed socket (Adam: a 502 and a charged buyer on testnet). 30 s fits 97 % of the settlements 0043 measured (Adam's reading). Config now bounds the budget to 1–80 s and the timeout to at most the budget.
18. **`main()` refuses `stellar:pubnet` while `STORE=memory`** (second review). This PR makes `/settle` spend, with a store a restart loses, allow-all spend hooks, no rate limit and no lease. The check is in `main()`, not `parseConfig`, so the config tests can still parse a pubnet config; 0022 lifts it with a durable store. Superseded by 0022: its config refuses `STORE=memory` outside testnet, before `main()` runs, so the check is gone and the test expects the config's message. Its other three reasons are back as decision 49.
19. **The one-payer-entry rule is a `/verify` check** (second review). Upstream de-duplicates signers and doesn't count entries, so `/verify` said valid for two payer entries and only `/settle` refused them: the seller served the request for free, as often as the signature lasted. `createChecker` now rejects them with `invalid_exact_stellar_payload_payer_auth_entries` and hands `/settle` the nonce.
20. **Every store and hook call is bounded, and the budget answer never throws** (second review). Before the claim, a store that doesn't answer within the budget is a 500, as a store error was. After it, `beforeSubmit` and the store calls are bounded by what is left of the budget, and the budget's own write, the success mark and each poll by the store's grace (1 s, the `STORE_GRACE_MS` constant in `settle.ts`, not a setting), so the longest call stays below the ALB's 120 s. Amended by decision 32: the checks are bounded too, and the claim gets at least the grace. `endUnsigned` never throws: when the store fails, the answer is what the call knows, `settlement_pending` with the last hash `onSigned` was given, or `…_timeout`. A budget-over flag makes `onSigned` refuse every new hash once the budget answer is out, so a `txBadSeq` rebuild can't land under a hash the answer didn't name. A timeout per store call in the adapters is 0019's (0022 closed without one).
21. **A `beforeSubmit` that doesn't answer within the budget ends the record as the budget does,** with `onFinal` (hooks.ts says so). 0024's `onFinal` must accept a reservation that doesn't exist. Amended by decision 34: `onFinal` runs only once the hook has settled, so a late reservation is released too.
22. **Repeats share one store read per poll per key, and stop when their client leaves** (second review: 1,000 repeats held the event loop). One read is shared by every repeat of a key in each interval, and the route aborts a repeat whose client closed the connection.
23. **`RpcTimeoutError` before anything was signed answers `settle_exact_stellar_rpc_unavailable`** (second review). It used to be `unexpected_settle_error`, which reads as a bug. The record still ends, so the client signs a new payment, but it can tell "try later" from a bug.
24. **`…_nonce_already_used` carries the stored hash, if any** (second review: a front-run with only `extra` changed landed, and the real seller got `transaction: ""`). Never the outcome, never `success`.
25. **`/settle`'s own fee refusal is a drift too** (second review). Its re-check answers upstream's `invalid_exact_stellar_payload_fee_exceeds_maximum`, which is now logged and counted like the pool's refusals (decision 10); the set uses the `SETTLE_REASONS` constants.
26. **One origin per transition** (second review). A late success ran `onFinal(…, "settle")` and `onSuccess(…, "resolved")`. Now the call's origin turns `resolved` when its budget answer goes out, and both hooks get the origin of the write that finished the record.
27. **`FakeRpc` is exported as `@stellar-x402/signer-pool/testing`** (answers 0020's question; second review). `settle-pool.test.ts` runs `buildSettlement` on the real pool: a settlement, `/settle`'s floor of 2 ledgers, the pool's fee ceiling and the budget. The `attemptsOf` mock stays for the settler's unit tests: the real pool throws with a `sent: "unknown"` attempt only on paths `FakeRpc` can't reach (Adam: unreachable with the current pool).
28. **Metrics and logs for the rest** (second review): the counters decision 38 lists, then under two prefixes. `settled` carries the settlement key and a `replay` flag, and `settlement_hook_failed` the network and key. The store port says that `addHash` is atomic with `transition`, and the contract tests check it and `markSuccessAnswered`.
29. **A success the store can't mark is answered once per process** (okarcz, 2026-10-16, option A of Adam's third review; ADR 0006 amended). When `markSuccessAnswered` throws or misses the grace, the payment still landed, so the caller gets the success (decision 16). Every caller used to be "first" while the store was down: N successes and N headers for one payment. Now a process-local set holds each key whose mark is in flight, failed, or was never tried because the success came from the pool's result with the store down (decision 15). Concurrent and later callers in the process get `…_already_settled`. A key leaves the set once the store has answered the mark, so the set grows only during a store outage. Known exception until 0019: after the store recovers, or on another instance, a repeat can win the mark and get a second success. The other option, `settlement_pending` with the hash on a mark failure, keeps success-once strictly, but a seller whose store stays down would never get its success.
30. **The store-outage rule: refuse before money moves, tell the truth after** (okarcz, 2026-10-16; ADR 0006, task 0013). A store that fails before or at the claim is a 500 and nothing is sent; at the hash write before a send, the pool doesn't send (AD-16); after the pool answered, the answer is the pool's result and the record stays unfinished (amended by decision 52: not for a refusal the store can't record); at the success mark, decision 29. So an outage stops new payments without losing money, and a payment caught in flight still gets an honest answer. 0019 repairs unfinished records after the store is back; ADR 0012 (from 0013) sets how available the store is; 0027 alarms on `settlement_record_failures_total`.
31. **A repeat that can't end an unsigned record answers `settlement_pending` with no hash** (Adam's third review). `record = (await endUnsigned(key)) ?? record` used to fall back to the stale `claimed` read and answer `…_timeout` ("never will be signed"), while another instance, or the first call, could still sign and land it: the buyer would pay twice (reproduced with two settlers on one store, clocks 150 ms apart). Unknown is never "sign a new payment".
32. **The checks run inside the budget, and past it nothing is claimed** (Adam's third review, with #45's trial merge). `deps.check()` is bounded by what is left of the budget. A check past it, or one that ends with no budget left, answers `…_timeout` before the claim: nothing is recorded, so the same payment may be sent again as it is. The claim itself is bounded by at least the store's grace: with `left()` near 0 a real store's claim lost the race to a 0 ms timer, answered 500 and landed anyway. ADR 0011 has the checks' worst cases: up to 91 s with #45's 3 URLs and a fee-stats bid, so a hung RPC set can make a valid payment time out.
33. **A repeat's waits end by its own budget** (Adam's third review). `pendingUntil` was anchored on the repeat's own start, after a known-key lookup bounded only by the budget, so a slow store took a repeat to about 163 s at 80/80. Both waits are now also capped at the repeat's `startedAt + SETTLE_BUDGET_MS`; ADR 0011 says the budget path can spend up to 2 × 1 s on its last writes.
34. **`onFinal` after a `beforeSubmit` past the budget runs once the hook settles** (Adam's third review; amends decision 21). `bounded()` doesn't cancel the hook, and `onFinal` used to run at once: a hook reserving after that kept its reservation forever (a probe printed `onFinal(release) → reserved`). `endUnsigned` takes the hook's promise and runs `onFinal` after it, whatever it answers.
35. **`onSigned` checks the budget flag again after `addHash`** (Adam's third review; for 0022, now 0019's). With a slow store, the budget answer could read `[h1]` while `addHash(h2)` was in flight and then resolve `true`, and the pool sent h2. Now a hash stored after the budget answer is never sent. The memory store can't interleave there; a durable one can.
36. **`FallbackRpc` throws `RpcUnavailableError` when every endpoint failed** (Adam's third review; signer-pool). It used to rethrow the first endpoint's own error, so all RPCs refusing connections answered `unexpected_settle_error` ("tell us"). Now the error has the first one as `cause` and maps to `settle_exact_stellar_rpc_unavailable`. A not-found answer (`isNotFound`) is thrown as it is: the endpoint answered, and the pool's channel quarantine depends on it.
37. **Auth entries without address credentials are refused by `createChecker` and the pool** (Adam's third review, security). A source-account entry authorizes as the operation source, which the pool makes the facilitator, and only upstream (`~2.28.0`, floating patches) refused it. `/verify` and `/settle` answer upstream's `invalid_exact_stellar_payload_unsupported_credential_type`; `SettlementSubmitter.submit` throws `SourceAccountAuthError` before it takes a channel (its doc no longer invites `require_auth` on the facilitator).
38. **One metric prefix, every metric listed** (Adam's third review, [0027]). The `settle_*` counters are renamed `settlement_*`, so log and metric names match:
    - `settlement_outcomes_total{reason, replay}`: every answer, `success` or the `errorReason` (new; 0027 AC 1);
    - `settlement_already_settled_total`;
    - `settlement_nonce_reuse_total`: counted before any check, so a forged body can raise it;
    - `settlement_refused_after_verify_total{reason, stage}`: `stage` is `pool` after the checks passed, or `check` for `/settle`'s own re-check, which a payload `/verify` never saw can trigger; alarms watch `pool`;
    - `settlement_budget_exhausted_total{signed}`;
    - `settlement_uncertain_total`, `settlement_record_failures_total`, `settlement_submit_failures_total`;
    - `settlement_hook_failures_total{hook}`;
    - `pool_events_total{type}`, plus `status` on `resolved` for a "pending settlements" alarm.
39. **A request body nested deeper than 32 levels is a 400** (Adam's third review). The fingerprint's `canonical()` recurses once per level, so about 60 KB of nested arrays under `extensions` threw `RangeError`: a free 500 and an error log per request. `parsePaymentRequest` counts the depth without recursion, for `/verify` and `/settle` alike.
40. **`SETTLE_TIMEOUT_MS` defaults to the shorter of 20 s and the budget, and needs at least 1 s** (Adam's third review). Setting only `SETTLE_BUDGET_MS=15000` failed startup on a default the operator never set, and 1 ms was allowed, which no seller retry can use.
41. **Logged errors keep only the host of each URL** (Adam's third review). The logger's replacer ran no redaction, so an RPC error message with a path API key reached `settlement_submit_failed` as it was. It now uses the same `redactedError` as `captureConsoleError`.
42. **`main()`'s parts come from `compose(config, …)`, tested on the real pool** (Adam's third review). Nothing tested `onSuccess: cataloger.onSuccess`, `extensionResponses` or the one `fees` shared by the checks and the pool; replacing any of them passed every test. `settle-pool.test.ts` now settles a bazaar payment through `compose()` (header, then the catalog entry after the response) and checks that `/verify`, `/settle` and the pool read the fee-stats bid once. `buildVerifier` is documented as a test seam.
43. **`<package>/testing` subpaths are test-only, by a lint rule** (Adam's third review). `no-restricted-imports` refuses `@stellar-x402/*/testing` in `apps/*/src` and `packages/*/src`; the convention is in the spine's conventions table.
44. **RPC endpoints are logged as `RPC_URLS[i]`, never by URL or host** (Adam's third review, with #45; ADR 0011 amended). ADR 0011 said "by host only", while #45 names its switches `RPC_URLS[i]`, which is safer: a host can name a paid provider. A URL inside an error message is still reduced to its host. `FallbackRpc` keeps full-URL names until 0049/0027.
45. **#41 merges first; #45 rebases onto it** (okarcz, 2026-10-16). The rebase must:
    - spread `buildUpstream()` into `buildChecks`, so `/settle` gets the failover and its deadline;
    - give `Check` the `VerifyTrace` argument, or `verified.rpc` stays empty for `/settle` (the trial merge auto-merged `trace` into `createChecker`'s arrow without it);
    - fix `settle-pool.test.ts`, which calls `buildChecks` positionally and breaks on the new `logger` argument;
    - add a `/settle` test with a hung first RPC URL, which decision 32's bound now answers `…_timeout` before the claim when it outlasts the budget;
    - (Adam's sixth review) thread its seams through `compose()`, where `FallbackRpc.fromUrls` lives since the rebase onto 0022; rename `upstreamAtCurrentBid` to `atCurrentBid`; pass `jsonLogger` its third argument, `config.rpcUrls`, and name switch logs with `rpcEndpointName` (decision 47).
46. **A repeat ends an unsigned record only once the first call's budget has ended** (Adam's fourth review). Decision 33 capped the unsigned wait at the repeat's own budget, and the repeat then ended the record. On the lost-claim path the repeat began before the winner, so its budget ends first, and it ended the winner's record while the winner could still reserve or sign: `onFinal` ran before a late `beforeSubmit` settled (against decision 34), and a winner still waiting for a channel had `addHash` refused and answered `…_timeout` with budget left. Now the wait is still capped by the repeat's own budget, but if the first call's budget (`createdAt + SETTLE_BUDGET_MS`) hasn't ended, the repeat answers `settlement_pending` with no hash ("not signed yet: repeat the same payment") and leaves the record. Across instances a repeat judges this by its own clock, so 0024 keys a reservation by the settlement key and refuses a reserve after its release.
47. **An `RPC_URLS` entry is logged as `RPC_URLS[i]#<fingerprint>`, also inside error messages** (Stan's review, okarcz, 2026-10-20; ADR 0011 amended). Decision 44 still reduced a URL in an error message to its host, against ADR 0011's "never by host": a host can be an account's own endpoint name or an internal one. `redactUrls` now names a URL that starts with an entry (the longest), or is on an entry's host, by `rpcEndpointName`; any other URL, such as Horizon's, keeps its host. The fingerprint is the first 8 hex digits of the entry's SHA-256: `RPC_URLS[2]` can mean another URL after a redeploy, and the fingerprint tells the two apart. #45's switch logs take the same names on its rebase.
48. **`markSuccessAnswered` in PostgreSQL is one conditional `UPDATE`** (the rebase onto 0022, 2026-10-20). 0022 merged first, without the port's new method. Migration `0002_success_answered` adds a nullable `success_answered_at bigint`: an expand step, so the release before it keeps working. `UPDATE … SET success_answered_at = $2 WHERE key = $1 AND state = 'success' AND success_answered_at IS NULL`, and `true` for exactly one caller: the row lock serializes them, and the second sees the column set. The contract tests from decision 16 now run on PostgreSQL too. `addHash` already locks the row (`FOR UPDATE`), which makes it atomic with `transition`.
49. **The config refuses `stellar:pubnet` until 0023, 0024 and 0025 land** (Adam's sixth review, okarcz, 2026-10-20). 0022's rule covers only the first of decision 18's four reasons, so a pubnet config with `STORE=postgres` started a `/settle` that spends with an allow-all `beforeSubmit`, no rate limit and no lease: a self-made SEP-41 token whose `transfer` emits one correct event passes `expectTransfer`, and every self-payment costs us up to 0.025 XLM in fees. One hard rule after the `STORE` one, not an opt-in flag: a flag ends up in an env file (`deploy/mainnet.env.example` exists), and no task needs pubnet before these land. One rule for all three, its message naming them; each task has a "From 0009" bullet, and the last to land removes it. The lease's place on the list is an assumption that 0025 confirms. "Maps every setting" now parses testnet, the only `NETWORK` that parses. Folded into the commit that added `main()`'s check, so every commit passes `pnpm test`.
50. **A repeat counts its `SETTLE_TIMEOUT_MS` from the hash it first sees** (okarcz, 2026-10-20, Adam's sixth review). It was fixed at the repeat's arrival, so a repeat that waited for the signing (up to the first call's budget) could find its 20 s already over when the hash appeared, and answered `settlement_pending` at once though its own budget ran on: one more retry for the seller. Now `hashSeenAt` is set on the first read with a hash, still capped by the repeat's own budget.
51. **The success goes to whoever marks first, not always the call that submitted** (okarcz, 2026-10-20, Adam's sixth review). On PostgreSQL a repeat's poll can read `success` between the submitter's `transition` and its mark. Still one success and one `onSuccess` (AD-6); `respond`'s doc and the concurrent test's name say so.
52. **A pool refusal the store can't record is answered `unexpected_settle_error`** (okarcz, 2026-10-20, Adam's sixth review; ADR 0006 amended). Decision 30 promised the pool's result after the pool answered; when the pool threw a refusal and `finish()` failed, there was no fallback. The code stays: it takes two failures in a row, and the record is still open, so a repeat could answer otherwise than the refusal's reason.
53. **The checks refuse an auth expiry past ledger 2^32 − 2** (okarcz, 2026-10-20, Adam's sixth review). A huge `maxTimeoutSeconds` signs to `0xFFFFFFFF`; `/verify` accepted it, and `submit()` threw `RangeError` on its `maxLedger`, so `/settle` answered `unexpected_settle_error` with nothing sent. `createChecker` now answers `invalid_exact_stellar_signature_expiration_too_far`, on `/verify` too.
54. **Logs: the fingerprint's limit is accepted, and `file:` URLs are kept** (okarcz, 2026-10-20, Adam's sixth review; ADR 0011 amended). An unsalted 8-digit SHA-256 prefix lets anyone holding a log confirm a guessed URL with few unknowns; the logs are ours, and an HMAC would add a secret per deployment while 0047 is open. The redaction also turned stack locations (`file:///…/x.js:10:5`) into an empty host; a `file:` URL is now kept as it is, while every other scheme (`postgres://` too) is still redacted.
55. **The test-helper lint rule also refuses a dynamic `import()`** (okarcz, 2026-10-20, Adam's sixth review). `no-restricted-imports` doesn't see `ImportExpression`, so a `no-restricted-syntax` selector covers it. `packages/signer-pool/test/testing-imports.test.ts` runs ESLint on fixtures, so dropping a pattern fails a test.
